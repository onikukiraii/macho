# バックエンドのテスト

テストの実行は pytest（`mise run test`）を使用する。実装コード側の規約は [backend.md](./backend.md) を参照。

## 4種類のテストと配分

テストコードは、機能ディレクトリと対応させて `tests/<機能>/` 配下に配置する。

| ファイル | 対象 | 使用するもの |
|---|---|---|
| `test_pure.py` | `_pure.py` の純粋関数 | なし（外部依存なし） |
| `test_service.py` | ユースケースの処理フロー | `tests/fakes.py` の Fake 実装 |
| `test_repository.py` | SQL クエリの正確性 | `db_session` fixture（SQLite インメモリ） |
| `test_router.py` | HTTP の入出力とルーティング | `client` fixture と `dependency_overrides` |

**4種類の中で `test_pure.py` を最も手厚く作成する。** DB やモックが一切不要で数ミリ秒で実行でき、テストが失敗した際も原因の特定が容易であるためである。計算や入力検証のロジックを `_pure.py` に集約しておけば、この層のテストだけで境界値を十分に網羅できる。

`test_repository.py` は、SQL の記述ミスやマッピング不整合を検知するための層である。Protocol の型チェックでは SQL クエリ内部の構文まで検証できないため、実際にクエリを発行して動作を確認する必要がある。

`test_router.py` は、HTTP ステータスコードとレスポンス形式の検証に絞る。ビジネスロジックの網羅的なテストをこの層で行ってはならない。同一の検証を全4層で重複して行うと、1つの仕様変更で4箇所のテストが同時に壊れてしまい、メンテナンスコストが増大する。

## 命名

- テストクラス名は `Test<対象の関数名>` とする。たとえば `notify_rest_finished` のテストは `TestNotifyRestFinished` とする。
- テストメソッド名には、何を検証するのかを日本語で具体的に記述する。たとえば `test_停止すると終了時刻になっても通知しない` とする。
- メソッド名自体で意図が十分に伝わるため、テストメソッドに docstring は記述しない。
- テスト名と実際の検証内容を常に一致させる。テスト名を変更せずに検証項目だけを追加してはならない。

## Fake を使い、モックライブラリを使わない

外部サービスとの境界はすべて Protocol で抽象化されているため、`unittest.mock` や moto などの外部モック環境は不要である。テストには `tests/fakes.py` で定義した Fake 実装を注入する。

- Fake 実装は `tests/fakes.py` に集約し、各テストファイルで個別に再実装しない。
- Fake 実装には検証に必要な状態を持たせる。`FakeJobQueue.enqueued` や `FakePushSender` が記録した送信を直接アサートすることで、「意図した引数が正しく渡されたか」を外部から検証できる。
- 特定のテストでのみ使用する異常系用の Fake は、そのテストファイルの末尾に `_FailingJobQueue` のようなプライベートクラスとして定義する。`fakes.py` に異常系実装を並べると、共通で利用する正常系 Fake の見通しが悪くなるためである。
- プロダクションコードの内部ロジックを `mocker.patch` で差し替えてはならない。内部を差し替えたくなった場合は、その境界が Protocol で適切に抽象化されていないサインである。

## fixture

各 fixture は `tests/conftest.py` に定義されている。

- `db_session`: テストケースごとに初期化される SQLite インメモリ DB のセッション。外部キー制約は有効化されている。
- `client`: `get_session` を `db_session` に差し替えた FastAPI の `TestClient`。

`dependency_overrides` を変更した場合は、テスト終了後に必ず元の状態へ復元する。fixture の `yield` 直後、または `finally` 節で `app.dependency_overrides.pop()` を実行する。`app` インスタンスはモジュールスコープで共有されるため、設定が残ったままだと後続のテストに影響を及ぼすためである。

## 期待値の書き方

- 期待値には、実装コードで定義されている Enum や定数を使用する。たとえば `assert result is PushResult.expired` と書く。文字列リテラルで記述すると、その `"expired"` がどの定義値を示しているのか判別しにくくなる。なお、Enum の同一性検証には `is` 演算子を用いる。
- 値そのものが外部システムとのインターフェース契約になっているもの（API レスポンスのキー名や文字列、フロントエンドが参照するプロパティなど）は、値の一覧を突き合わせる専用のテストを1本定義し、リテラルはそこにのみ記述する。個別のテストケースごとに期待値を文字列リテラルで記述しても契約の保証にはならず、仕様変更時に修正箇所が無駄に増えて形骸化する原因となる。
- テスト内で `assert` を条件分岐させない。ケースごとの入力と期待値は `pytest.mark.parametrize` のパラメータとして定義する。分岐を含むテストは、分岐ロジック自体が破綻していても見かけ上パスしてしまう危険があるためである。
- 1つのテストケース内に複数の検証事項を詰め込まない。確かめたい観点が2つあるなら、テストメソッドを2つに分割する。
- HTTP ステータスコードの検証だけでなく、レスポンス内の `status` などの結果フィールドも合わせてアサートする。

## ケース設計

- 過剰に網羅しようとして複雑化させず、1つのケースで関心事が完結するように整理する。
- 実装に分岐を追加した場合は、その分岐をカバーするテストも追加する。複雑度の警告が出た際は、安易に `# noqa` で抑制する前にリファクタリングを検討する。
- 例外発生時の処理フローも必ず1本はテストを通す（例: 対象データが存在せず `NotFound` を送出する `get`、障害発生を記録してから例外を再送出する service など）。
- 認可制御を伴う機能では、「許可される操作」は必要最小限の権限で検証し、「禁止される操作」は必要最大限の権限で検証する。管理者などの強い権限のみでテストを通してしまうと、本来拒否すべきアクセスを見逃す原因になる。
- テストコードにおいては、DRY（重複排除）よりもテストの網羅性と独立性・明確さを優先する。過度に共通化を進めると、実装変更時に影響を受けるテストの範囲が把握できなくなり、機能を削除する際に関連するテストケースだけを安全に削除できなくなるためである。
