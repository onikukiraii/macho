# バックエンド

FastAPI + SQLAlchemy + Alembic / Python 3.14 / パッケージ管理は uv。

ディレクトリ構成や配置ルールは [architecture.md](./architecture.md)、テーブル設計とクエリ規約は
[database.md](./database.md)、テスト方針は [backend-test.md](./backend-test.md) を参照。
本ドキュメントでは、具体的なバックエンドコードの実装規約を定める。

## 型と値

mypy は strict 相当の設定で動作している。型チェックを通すために安易に型注釈を外してはならない。

- 公開する関数の戻り値には必ず型注釈を明記する。型推論に任せてしまうと、戻り値を変更した際に型定義が暗黙のうちに変化し、型チェックでデグレ（破壊的変更）を検知できなくなる。特に `dependencies.py` では徹底すること。
- 値の存在チェック（None チェック）は `is not None` / `is None` を用いる。`if x:` のような真偽値評価は、`0` や `""`、`[]` なども False と評価してしまい、正当な値が存在する場合でも欠損値として扱ってしまうためである。
- None を許容する型定義には `X | None` の形式を使用し、旧来の `Optional[X]` や `Union[X, Y]` は使わない。
- 文字列の列挙には `StrEnum` を使用する。JSON へのシリアライズが自然に行え、明示的な `str()` 変換が不要になる。
- 排他的な状態を `None` や番兵（sentinel）文字列で表現しない。判別共用体（Tagged Union）または `StrEnum` を用いる。`None` に状態の意味を持たせると、判定ロジックが「None か」「特定文字列か」「空文字列か」など実装者によってばらつく原因になる。
- Pydantic は v2 の API を利用する。`model_dump()` や `model_validate()` を使用し、非推奨の `dict()` や `**` によるアンパック展開は使わない。
- 型チェックを無理やり通すための `Any`、`cast`、`# type: ignore` は使用しない。型が合わない場合は、型定義または実装そのものを修正する。

構造が固定されたデータを、汎用的な `dict` や要素位置に依存する `tuple` のまま関数・モジュール間で受け渡してはならない。ドメインモデルには `types.py` で定義した `dataclass(frozen=True)` を、API のリクエスト／レスポンスや LLM の構造化出力には Pydantic モデルを使用する。

## 命名

- grep（全文検索）による検索のしやすさを基準に決定する。単なる `close` ではなく `close_review` のように、多少冗長であっても呼び出し箇所を確実に検索・特定できる名前を選ぶ。
- 意味が広すぎる `data`、`info`、`check`、`cnt` などの単語や、`*_data` という接尾辞は避ける。何をどのように処理するのかを「動詞＋目的語」で具体的に表現する。
- Protocol のメソッド名にはビジネスドメインの語彙を用いる。`select_with_where()` のような SQL やストレージ由来の語彙をインターフェースに漏らさず、`list_published()` のように業務上の意味で命名する。
- entity クラスは `XxxRow`、ドメインモデルの型は `Xxx` とする。
- 対になる概念は名前も対称性を持たせる（例: `create_running` に対する `save_succeeded` / `save_failed` など）。
- 名前と実際の実装内容を常に一致させる。処理内容や責務が変更された場合は、名前に引きずられず適切にリネームする。

## 関数

- 引数が3つ以上ある場合や、同じ型の引数が連続する場合は、キーワード専用引数（`*`）にする。これにより、呼び出し側でどの引数に何を渡しているかが明確になる。
- ガード節（バリデーションや事前条件チェック）は関数の先頭にまとめる。関心事の異なるガード節は同一行にまとめず、行を分けて記述する。
- 条件判定は原則として肯定形で記述する。分岐が3つ以上になる状態処理には、多重 `if` を避け `match` 文や辞書引きを活用する。
- 複雑な条件式は意味のわかる説明変数に切り出す。適切な命名を行うことで、補足コメントが不要になることが多い。
- 引数を省略した際に、安全ではない挙動（非フェイルセーフな側）に倒れる設計にしない。デフォルト値は常に安全で制限の厳しい側に設定する。
- コードのネストは早期 return（early return）を活用して浅く保つ。

## router

```python
router = APIRouter(prefix="/exercises", tags=["exercises"])


@router.get("/{uid}")
def get_exercise(uid: str, repo: Annotated[ExerciseRepository, Depends(get_exercise_repository)]) -> ExerciseDetailResponse:
```

- 引数の型注釈には `protocol.py` で定義したインターフェースを指定し、`Depends` には `dependencies.py` のプロバイダ関数を渡す。
- 関数名は `get_` / `create_` / `update_` / `delete_` + リソース名とする。
- デコレータの `response_model` 引数は使用せず、関数の戻り値の型注釈でレスポンス型を指定する。
- ドメインモデルからレスポンス DTO への変換処理は、各 router ファイル末尾の `_to_response()` 関数に集約する。
- 1つのリソースにつき1つのファイルを作成する。作成したルーターは `main.py` の `app.include_router` に追加して登録する。

## dto

- DTO の命名規則は、リクエスト用を `XxxCreateParams`（または `XxxUpdateParams` など）、レスポンス用を `XxxResponse` とする。
- リクエスト入力のフォーマットや値の範囲チェックは Pydantic の `Field` などで行う。同一のバリデーションを `_pure.py` で重複して記述しない。
- API レスポンスには内部の連番 `id` を含めず、UUID である `uid` を返却する。`id` は内部的な自動採番キーであり、外部から意味を特定しにくいためである。新規に実装する機能では `exercise` の設計に倣うこと。

## エラー

ドメイン例外は `common/errors.py` に定義し、`router.py` で対応する HTTP 例外に変換する。変換対応はプロジェクト全体で一貫性を保つ。

| ドメイン例外 | HTTP ステータスコード |
|---|---|
| `NotFound` | 404 |
| `Forbidden` | 403 |
| `BusinessRuleViolation` | 400 |
| `Conflict` | 409 |
| `JobQueueUnavailable` | 503 |

- `service.py` で `HTTPException` を送出してはならない。Celery ワーカーなど非 HTTP 環境から再利用できなくなるためである。
- 外部ライブラリ固有の例外は具象実装内でキャッチし、ドメイン例外に変換して再送出する。`ClientError` や `IntegrityError` などの例外が上位層に漏れ出すと、上位層が外部ライブラリに依存してしまう。
- 例外を握り潰してログ出力だけで済ませる `except` ブロックを書かない。回復不能な例外はそのまま送出する。意図して例外を抑制する場合は、その正当な理由をコメントに明記する。
- 外部システムから返されたエラー本文をそのままクライアントに返却しない。詳細なエラー内容はログに記録し、クライアント向けには定型の安全なエラーメッセージを返す。
- 例外メッセージには、調査の足がかりとなるキー（クライアントから渡された `uid` や `job_id` など）を含めてよい。ただし、内部の連番 `id` はレスポンス本文に漏洩する経路が存在するため含めない。
- `or "{}"` のような本質的な解決にならない不適切なフォールバック処理は書かない。空応答を別の不可解なエラーにすり替えてしまうだけであるため、無理に握り潰さず素直に例外として失敗させる。

## 過剰な防御を書かない

- 信頼できる内部の呼び出し経路に、不要な `try` / `except` や存在チェックを配置しない。入力検証は信頼境界（トラストバウンダリ）でのみ行う。ここでの境界とは、API の受け付け口および外部システムからのレスポンスをパースする箇所を指す。
- 静的型チェックによって値が保証されている場合は、実行時に重複して同じバリデーションを行わない。
- 仕様上発生し得ない事態に対する過剰なフォールバック処理は書かない。
- null ガードは、値を利用する側ではなく値を定義・生成する側に設ける。利用側に設けると、すべての呼び出し箇所で重複したガード処理を書くことになる。
- 過剰に防御的な実装はコードレビューで容認されやすく、一度マージされると削除する契機がないまま複雑性を増していく。追加する明確な根拠を簡潔に説明できないコードは書かない。

## コメント

原則としてコメントは書かない。記述を許可するのは、コード自体から読み取れない設計上の理由、外部リソースへの参照リンク、意図的な妥協とその許容範囲、非自明な前提条件のいずれかに該当する場合のみとする。コードの単なる言い換え、変更履歴、処理ブロックの区切り見出しなどは書かない。また、コード本体に対して過度な密度のコメントを残さない。

## ログ

- ロガーの取得には `logging.getLogger(__name__)` を使用する。標準出力用の `print` は使わない。
- 例外を再送出せずにその場で記録する場合は、`logger.exception` を使用してスタックトレースを残す。
- ログにパスワード、トークン、個人情報（メールアドレス本文など）をはじめとする機密情報を出力しない。

## 設定

環境変数の読み込みは `common/config.py` の `Settings` クラスに集約し、`settings` インスタンス経由で参照する。各モジュールで `os.environ` を直接参照してはならない。また、新しい環境変数を追加した際は、必ず `.env.template` にも追記する。設定値の定義がコード内にしか存在しないと、他の開発者がその設定の存在を認識できなくなるためである。

## Lint とコマンド

```bash
mise run lint     # ruff check / ruff format --check / mypy
mise run format   # ruff check --fix / ruff format
mise run test     # pytest
mise run dev      # 開発サーバー
mise run worker   # Celery ワーカー
```

- Ruff: line-length=120、select=[E, W, F, I, B, UP]。
- `B008` は FastAPI の `Depends` パターンを許容するために無視（ignore）している。
- `worker.*` の `untyped-decorator` は、Celery が `py.typed` を持たないため無効化している。
- 設定ファイルには、ツールのデフォルト値と同じ設定を明示的に記述しない。ツール側のデフォルト値の改善やバージョンアップに追従できなくなるためである。
