# データベース

SQLAlchemy 2.0 スタイル + Alembic / MySQL。テスト環境は SQLite のインメモリ DB で動作する。

新規テーブルを作成する手順は [new-model.md](../../docs/new-model.md) を参照。本ドキュメントでは、データベース設計および実装に関する設計指針・規約を定める。

## テーブル定義の置き場

すべてのテーブル定義は `common/db/entities/` に集約し、`common/db/entities/__init__.py` に import と `__all__` への登録を行う。Alembic の `target_metadata` は単一のメタデータを通じて全テーブルを検知しているため、定義を各機能ディレクトリへ分散させると、`__init__.py` への追記漏れがあった際に「テーブルが削除された」と誤認され、マイグレーション自動生成で意図しない `op.drop_table()` が生成されてしまうためである。

各機能ディレクトリの `types.py` に SQLAlchemy の `Mapped` を持ち込んではならない。逆に entity 側には、バリデーション上限値などのアプリケーションポリシーに関する定数を配置しない。テーブル定義が担うのは物理スキーマの表現のみであり、業務ポリシーは `_pure.py` で管理する。

## カラム

- クラス名は `XxxRow` とする。ドメイン型の `Xxx` とクラス名で明確に区別できるようにする。
- `uid` カラムは `id` の直後に定義する。外部クライアントには `uid` を返し、内部的な連番 `id` は公開しない。
- 状態（ステータス）のカラムは entity では単純な `str` として保持し、`StrEnum` への変換は `repository.py` の `_to_domain()` で行う。entity が Enum に依存すると、DB 内に想定外の不正値が存在した際のハンドリングがデータアクセス層に漏れ出してしまうためである。
- 最大長を見積もれる文字列カラムには `Text` ではなく `String(長さ)` を指定する。上限を見積もれない長文テキストのみ `Text` を使用する。
- `datetime` カラムはすべて UTC で保存する。`default=lambda: datetime.now(UTC)` を使用し、タイムゾーン情報を持たない（naive な）datetime を混在させない。
- 同じ制約を複数箇所に分散して定義しない。桁数や文字列の上限値は entity 側の定義を一意の基準（Single Source of Truth）とする。
- カラム名に外部システム固有の概念や命名を持ち込まない（例: 外部サービス変更の影響を受ける `algo_job_id` ではなく、機能ドメインに基づく `review_job_id` とする）。
- MySQL の予約語（`trigger` など）をカラム名に使用しない。
- 複合ユニーク制約は `UniqueConstraint` で明示する。複合インデックス `[A, B]` が存在する場合、先頭カラム `A` 単独のインデックスは別途張らない。B-tree インデックスは最左プレフィックス一致により、複合インデックス側で単独カラムの検索もカバーできるためである。

## リレーション

- `back_populates` を双方向で設定する。
- 親子関係には `cascade="all, delete-orphan"` を指定し、親レコードの削除に伴って関連する子レコードも連動して削除されるようにする。
- 子レコードの `relationship` には `order_by` を指定する。指定しない場合、クエリ発行ごとに子レコードの取得順序が不定になる。
- 子レコードを一括で差し替える際は `row.items = [...]` のように再代入する。関連から外れた古いレコードは `delete-orphan` によって自動削除される。
- 循環 import は `TYPE_CHECKING` ガードと文字列による前方参照を用いて回避する。`from __future__ import annotations` は使用しない。

## クエリ

- 一覧取得クエリには必ず `order_by` を明示する。MySQL は明示的なソートがない場合に行の順序を保証しないため、ページネーション時にデータの重複や欠落が発生する。デフォルトの並び順は `id` 昇順とする。`updated_at` 順はレコード更新のたびに表示順が入れ替わり、画面表示が不安定になるため避ける。
- リレーションを持つ entity の一覧取得には `selectinload` を指定して N+1 問題を防ぐ。`joinedload` の利用は1対1のリレーションや取得件数がごく少数に限定される場合にとどめる。
- 単一行の取得において、主キーやユニーク制約で一意性が保証されている場合は `scalar_one_or_none()` を使用する。想定外に複数行が取得された際に例外が発生し、データの不整合を検知できるためである。非ユニークな検索条件の場合や `joinedload` と併用する場合は `.scalars().first()` を用いる。
- ループ処理の内部で個別に INSERT を実行しない。親レコードに関連レコードをネストさせて一括で `add` するか、bulk insert を利用する。
- 同一レコードが複数の処理経路から更新される可能性がある場合は、すべての更新経路で `with_for_update()` による行ロックを取得する。一部の経路だけでロックを取得しても、競合相手の更新によって上書きされてしまう。
- 論理削除を採用しているテーブルでは、クエリの検索条件に必ず `deleted_at.is_(None)` を含める。論理削除を行う UPDATE 処理を複数箇所に分散させない（条件の記述漏れを防ぐため）。

## トランザクションと外部への書き込み

- `commit()` を呼び出すのは `repository.py` 内のみとする。`service.py` は処理手順のオーケストレーションに専念し、`router.py` にはトランザクションの知識を持たせない。
- S3 などの外部ストレージと DB への書き込みが伴う場合は、「DB の commit → S3 へのアップロード」の順序で行う。DB 側に先行して記録があれば、S3 アップロード失敗時に検知して再試行できるが、逆順にするとどこからも参照されない不要なオブジェクトがストレージ上に孤立して残ってしまう。
- データの移行を伴う削除処理は、「移行完了 → 削除」の順序で実行するか、同一トランザクション内にまとめる。削除処理を先行して commit すると、移行処理が失敗した際に元データが消失する。
- 一意制約違反（`IntegrityError`）は `repository.py` 内でキャッチし、`rollback()` を実行した上でドメイン例外（`Conflict`）に変換して再送出する。SQLAlchemy 固有の例外を上位層へ漏らさない。

## マイグレーション

```bash
docker compose up -d db
mise run migrate-gen "add products table"
mise run migrate
```

- 生成されたマイグレーションファイルは必ず目視で内容を確認する。意図しない `drop_table` や `alter_column` が含まれていないかを検証する。
- 生成後に `uv run ruff check --fix alembic/versions/ && uv run ruff format alembic/versions/` を実行してコード整形を行う。
- 変更内容が含まれない空のマイグレーションファイルは削除する。1つのテーブル新設は1つのマイグレーションファイルに集約する。
- コミット前にローカル DB 環境へ適用し、正常にマイグレーションが完了することを確認する。
