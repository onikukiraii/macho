# フロントエンドのテスト

Vitest + Testing Library / `mise run test:front` で実行する。実装側の規約は [frontend.md](./frontend.md) を参照。

## 配置と実行環境

- テストコードはテスト対象ファイルと同じ階層の `__tests__/` ディレクトリに配置する（例: `src/lib/utils.ts` のテストは `src/lib/__tests__/utils.test.ts`）。
- `src/test/setup.ts` で `@testing-library/jest-dom` のカスタムマッチャーを読み込んでいる。実行環境は jsdom であり、`globals: true` が設定されているため、`describe`、`it`、`expect` などのテスト API を各ファイルで import する必要はない。
- コンポーネントの描画には `src/test/utils.tsx` で定義されたカスタム `render` 関数を使用する。`@testing-library/react` の `render` を直接呼び出してはならない。Router などの必要な Provider がカスタム `render` 側に集約されているためである。

## 何を厚くするか

**`lib/` 配下の純粋関数を最も手厚くテストする。** 入力値と戻り値のみで結果が決まるため、テストが失敗した際も原因の特定が容易である。複雑な文字列のパースや状態整合性のロジックは、コンポーネント内に直接書かず `lib/` 配下へ純粋関数として切り出してテストを作成する。

コンポーネントのテストは、「画面上に実際に表示される要素」と「ユーザー操作の結果」の検証に絞る。内部のローカル state や特定関数の呼び出し回数といった内部実装の詳細は検証しない。

## 要素のクエリ（取得方法）

CSS クラス名で要素を取得してはならない。Tailwind CSS のクラスは純粋な見た目（スタイリング）の定義であり、寸法や色の変更のたびにテストが壊れてしまうためである。要素を取得する際は以下の優先順位で選定する。

1. ロールとアクセシブルネーム、または要素の状態（例: `getByRole('button', { name: '登録' })`、`getByRole('dialog')`）
2. 表示テキスト（例: `getByText('ユーザーが登録されていません')`）
3. テスト識別子（`data-testid`）

スクリーンリーダーによる読み上げで意味を持つ要素には、テスト都合だけでなくアクセシビリティ向上の観点から `aria-label` を追加してよい。それ以外の要素には `data-testid` を付与する。

## 書き方

- 期待値には、実装コードが保持している定数を使用する。ラベル定義マップが存在する場合はそこから参照する。実装側で定数定義されている値をテストコード側で文字列リテラルとして直書きすると、その文字列がどの状態のラベルに対応しているのか判別しにくくなるためである。
- 値そのものが外部システムとのインターフェース契約になっているもの（バックエンド API が返す値、localStorage のキー名、URL のクエリパラメータなど）は、値の一覧を突き合わせる専用のテストを1本作成し、リテラルはそこにのみ記述する。
- テスト内で `expect` を条件分岐させてはならない。ケースごとの期待値は `it.each` のパラメータとして定義する。条件分岐を含むテストは、分岐自体が機能していなくても見かけ上パスしてしまう危険があるためである。
- `describe` と `it` が1対1の関係になっている場合は、個別に並べず `it.each` でパラメータ化テストにまとめる。
- 1つの `it` ブロック内に複数の検証事項を詰め込まない。検証したい観点が2つあるなら、テストケースを2つに分割する。
- テスト名と実際の検証内容を常に一致させる。
- テストコードにおいては、DRY（重複排除）よりもテストの網羅性と明確さを優先する。過度に共通化を進めると、対象機能を削除する際に関連するテストケースだけを安全に削除できなくなるためである。
- テストヘルパー関数が返却するオブジェクトは、テストケース側で実際に参照・検証するもののみに限定する。

## API のモック

API を呼び出す関数は `src/api/fetcher.ts` に集約されているため、モック化もこの1箇所を差し替えるだけで完結する。

```ts
vi.mock('@/api/fetcher', () => ({
  usersApi: { list: vi.fn(), create: vi.fn() },
}))
```

グローバルの `fetch` 関数を直接差し替えてはならない。`fetch` を差し替えたくなった場合は、対象の API 呼び出しが `fetcher.ts` を経由していないサインである。

非同期処理による描画更新を待つ際は Testing Library の `waitFor` を使用し、`setTimeout` 等による固定時間のスリープを挟まない。

## 変換処理のテスト

ネスト（入れ子）構造を持つ入力データもテストケースに含める。配列内のオブジェクトなど階層構造を持つデータを検証しないと、再帰処理の破綻を検知できないためである。
DOM 構造の検証は、文字列の包含関係（`contains`）ではなく、要素ノードとその並び順で検証する。文字列の `contains` では、要素の入れ子構造や順序が崩れていても見かけ上パスしてしまうためである。
